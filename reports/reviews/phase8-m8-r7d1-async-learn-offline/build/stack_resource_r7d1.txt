    三条判读:
    a) diag 线程(rel_job_advance 的新增宿主): 帧 632→640(+8), 子树 1580→1588(+8)。
       栈配置 diagnosis.c:48 `#define DIAG_THREAD_STACK 4096`(本轮未改), 静态余量 4096-1588 = 2508 B。
       注意最深路径**不是**新增的 rel_job_advance(它 636), 而是 rel_prod_evaluate → rel_prod_publish
       → rel_ctl_take → rt_mutex_take → 调度器 → rt_scheduler_stack_check → rt_kprintf 这条既有线;
       也就是说 +8 B 全部来自 diag_thread_entry 自己的帧, 不是新调用线把上限顶上去了。
       rel_job_advance 的 636 里同样含 rt_mutex_take 那条调度器打印线, 不是它自己的活。
       帧这 +8 B 的来源只能说到这一层: diagnosis.c 本轮的唯一改动是一行调用
       (diagnosis.c:450-456, rel_job_advance(&in, have_frame, d_mode)), 没有新增任何局部变量;
       编译器为把这三个实参落地多占了一格, 而 armlink/fromelf 只给到"帧总大小"这一层, 不再给出
       是哪个槽 —— 所以这里登记为"实参/溢出槽增长", 不写成"新增了局部"。
    b) shell/命令线程(rel_cmd_* 的宿主): FINSH_THREAD_STACK_SIZE 4096(rtconfig.h, 本轮未改)。
       rel_cmd_learn 子树 +248 B 是**方向明确的一次换线**: 基线的最深跳是 rt_thread_mdelay(同步采集
       循环里的 20 ms 等待), 本轮 learn 不再等待, 最深跳换成 rel_job_start → rel_ctx_take →
       rt_mutex_take —— _rt_mutex_take → rt_thread_suspend_to_list 这一跳比 _thread_sleep 那一跳深。
       同时它的**自身帧反而小了**(296→168): 同步循环期的 rel_cap_*/rel_frame_to_input 全不在这条线上。
       可核对的拆分(把两件事分开, 不混成一个"+248"): 最深子树深度 = 子树总深 - 自身帧,
         基线 836-296 = 540(mdelay 线), 本轮 1084-168 = 916 —— 916 恰等于本轮 rel_job_start 自己的
         Max Depth, 说明 learn 的最深线就是它新受理作业那条; 净增 248 = 子树 +376 与自身帧 -128 之和。
       判据: 1084(learn)/1276(zero) 两条都小于 4096; 但 1276 不是"shell 栈总共用 1276"——
       armlink 不能把 msh_exec → 函数指针表里的命令处理函数连起来(finsh_thread_entry 的子树本轮仍是
       628, 与基线相同, 恰恰证明它没算命令处理函数), 所以"命令处理函数子树 + 分发点之上的 shell 帧"
       这个和没有工具支撑, 本轮不写成一个总数, 只登记两条子树各自的数与这个缺口。
    c) rel_cmd_zero +112 B: zero 仍是同步命令(任务书 §3 只要求 learn 异步)。它的帧 256→368 与子树
       1164→1276 **增量相同(都 +112)**, 且两版最深线一字不差都是
       rel_static_and_ready → motor_get_snapshot → mot_lock_take → rt_mutex_take… —— 所以这 112 B
       全部是 rel_cmd_zero 自己的局部, 不是任何被调用线加深。源码侧对得上: 现在函数开头是
