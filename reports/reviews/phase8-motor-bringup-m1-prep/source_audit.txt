2. 失败判定链的实现事实（本轮真实行号）
================================================================================
2.1 required 第 ④ 项把两种失败合并成一条消息 —— APP/safety_state.c:629-636
      629: /* ---- required ④ TMC2209 链路(初始化 + IOIN 读) ---- */
      630:     if (tmc2209_init() != RT_EOK ||
      631:         tmc2209_read_register(TMC_ADDR_DEFAULT, TMC_REG_IOIN, &v) != RT_EOK)
      632:     {
      633:         rt_kprintf("[SS] [REQ FAIL] TMC2209 link\n");
      634:         required_fail = -RT_ERROR;
      635:     }
      636:     else rt_kprintf("[SS] [REQ OK] TMC2209 (IOIN=0x%08X)\n", v);

    可观测性结论：**这条打印本身不区分是 init 失败还是 IOIN 读失败，也不带错误码。**
    启动日志里能拿到的只有"链路项失败"这一件事。这是后续包想要"可区分原因"时必须先解决的
    输出面限制（不是本轮修复项，见 §6）。

2.2 init 到底包含什么 —— APP/tmc2209.c:716-732
      718:  rt_err_t e = tmc_uart_open();            // uart2 设备 find/open
      725:  e2 = tmc_cfg_prod_sync();                // 执行器两把锁的建锁/同步
      727:  if (e != RT_EOK)      tmc_health = SUBSYS_FAILED;
      728:  else if (e2 != RT_EOK) tmc_health = SUBSYS_FAILED;
      729:  else                  tmc_health = SUBSYS_OK;
      731:  return (e != RT_EOK) ? e : e2;
    串口设备打不开或锁建不起来 ⇒ FAILED；两者都成功 ⇒ OK。

2.3 health 的迁移与语义 —— APP/tmc2209.c:704-714、734-740、824
      704:  * health 语义: OK=链路通且最近一次传输成功; DEGRADED=链路通但最近失败;
      705:  * FAILED=uart2 打不开; UNINIT=未初始化。
      711:  if (tmc_health == SUBSYS_UNINIT) return;   /* 未 init 时不越级判定 */
      712:  if (tmc_health == SUBSYS_FAILED) return;
      713:  tmc_health = (e == RT_EOK) ? SUBSYS_OK : SUBSYS_DEGRADED;
      738:  tmc_health_after_xfer(e);                  // 读 API 的唯一联动点
      824:  tmc_health_after_xfer(-RT_EIO);            // 传输层失败联动 DEGRADED

    supervisor.c:135 直接把 health 打进启动流：
      135:  rt_kprintf("[TMC]    %s drive_cfg=%s\n", subsys_health_name(tmc2209_get_health()), …

2.4 由此可以**从既有字节里排除两支**（这是本轮唯一能得到的正向缩小，不是猜测）
    启动流打的是 `DEGRADED` 而不是 `FAILED`。按 2.2/2.3 的迁移规则，DEGRADED 只有在
    health 已经离开 UNINIT/FAILED（即 2.2 的 e 与 e2 都成功）之后，被一次失败传输置起来。
    因此当时成立的是：
      · uart2 设备打开成功（原因树 A 的"设备找不到/打不开"被排除）；
      · 配置执行器两把锁创建成功（原因树 A 的"锁没建起来"被排除，
        并且 write gate 0x3B 里 bit6 NOT_SYNCED 确实为 0，与此一致）；
      · 失败发生在**其后的一次 IOIN 读**（safety_state.c:631 → tmc2209_read_register → 738 行联动）。
    同时 gate 位图给出旁证：0x3B = bit0 HW_NOT_VALIDATED(编译期宏)、bit1 MOTOR_NOT_QUIET、
    bit3 NOT_READY、bit4 FAULT_LATCHED、bit5 LINK_UNHEALTHY；**bit2 DRV_PAD_NOT_LOW=0、
    bit7 ENN_FB_NOT_DISABLED=0、bit6 NOT_SYNCED=0**。也就是说 MCU 侧请求电平、最终 ENN 反馈、
    锁同步都是好的，唯独链路不健康。位定义在 tmc2209.h:205-215。

3. 可区分原因树（每条写"现在能不能分、靠什么分"）
================================================================================
原因 A：uart2 设备/配置/互斥初始化失败
  A1 rt_device_find 失败 / A2 rt_device_open 失败 / A3 执行器锁创建失败
  → **本轮已由 §2.4 排除**（DEGRADED 而非 FAILED，且 NOT_SYNCED 位为 0）。
  错误传播：tmc2209_init() 的返回值直接进 safety_state.c:630 的或条件，被压成同一条 FAIL 文本；
  也就是说 A 类失败在**当前输出面上与 B 类不可区分**，只是这次恰好被 health 名称分开。

原因 B：总线读本身失败（发出读帧但没有合法应答）
  B1 无应答/读超时  B2 CRC 不符  B3 回显帧被当成应答  B4 短帧/丢字节  B5 地址不匹配
     B6 寄存器值合法但身份非 0x21  B7 应答来自别的器件
  → 现有字节**不能区分 B1..B7**（required 检查只回一个错误码，且不打印）。
  → 单条 `tmc_uart_probe` 能区分的部分（实现见 tmc2209.c:927-1003）：
     · :934-940 事务锁不可用 ⇒ 直接 REFUSED 且不发总线读（可区分"锁被占"与"总线坏"）；
     · :942-947 uart2 打不开 ⇒ 明确文本（与 A 类区分）；
     · :951-960 IOIN 首读失败 ⇒ 打印错误码并**立即结束**（不再锤总线），错误码可分 B1/B2 类；
     · :961-965 IOIN 读到后按 (IOIN>>24)&0xFF 判 0x21（B5/B6 可分；0x20=TMC2208）；
     · :967 起 GSTAT/IFCNT 各自还会再走一次超时（:923 注释已说明 IOIN 成功不代表后面不超时）。
  → probe **不能**区分的：B3/B4（帧形态细节，需要原始字节级取证而不只是 msh 文本）、
     以及"失败是接触性的还是电气性的"。

原因 C：启动时序（VM 未到位 / 模块上电晚于 MCU）
  → BOARD-B 那次是**供电之后主动复位**得到的启动流（§1.2），仍 FAIL，所以"USB 先插、VM 后开"
     这一条不能当作已定位的根因，也不能当唯一解释。
  → 残余不确定：复位到自检之间模块是否已稳定上电、PDN_UART 复位态、是否曾处于未插稳状态。
     这些只能由后续**已批准的现场包**在明确断电/上电次序下再观察一次；本轮不猜。

原因 D：PB6/PB7 与模块单线 PDN_UART 的连接、串联/合线电阻、模块地址与在位
  → 现有仓库里**没有原理图件、没有扩展板或模块照片**（本轮在 reports/ 与 BSP 文档、以及两处
     本地板级资料目录内检索均无图像/PDF 可依据；原理图 PDF 在
     reports/reviews/…safety-chain-acceptance-draft.md 里明确记为"未入库"）。
  → tmc2209.c:20 只登记了"uart2 / PB6=TX / PB7=RX / 115200 8N1 / slave addr 0"这个映射声明，
     其来源是早期硬件映射，不是本轮实测。IOIN bit6=1（PDN_UART 高）在历史读回里成立，
     说明"单线功能被启用"这一条在插好时是通的。
  → MS1/MS2 决定地址：mstep_reg_select=0（计划值是 0，tmc2209.c:1137），地址由硬件绑带决定，
     因此"默认地址 0 能不能应答"取决于模块上 MS1/MS2 的实际状态 —— **无实物依据，未知**。
     任务书 §5.1 已禁止拿"常见模块接法"替代该实物，本轮照办。

原因 E：SCI 功能时钟与 APB 使能域（波特率生成）
  → 既有材料存在"波特率按 PCLK2、使能位在 APB5"的疑点。本轮**只查真实调用链**、不改时钟、
     不下"波特率错四倍"的结论。
  → 支持"时钟链基本可用"的既有事实：同一条 uart2 在 20260925 拿到 100/100 合法应答、
     0 超时 0 CRC 错；同一固件同一时钟配置下 CRC 官方向量真机 PASS。若波特率系统性错，
     那 100/100 无法解释。=> 疑点保留为**需要测量回答的项**，不是本轮结论。

 · 读状态命令不推进门禁：tmc2209_get_write_gate_mask(:2057 注释"不产生总线流量")、
   motor_get_gate_fail_mask 都是只读观察口。
 · canonical 抑制/owner/phase：fault_reset 的"慢复核 + 一次最终提交"顺序在
   safety_state.c:59-63 的口径里写死（canonical 锁存/取消 owner/清码/写 MANUAL_CLEAR/换 epoch/
   最后清抑制），任何"先清抑制再改状态"的走法都不成立。
 · SW1 阻断与正式使能互斥：SW1 实测位（出处
   reports/reviews/phase8-sw1-hardware-cut-20261022/NOTES.txt:50-57，本轮实读）把 1-2 判为阻断侧、
   2-3 为允许侧（与图纸提取相反），
   因此 SW1 在阻断位时，许可拉 HIGH 之后的"使能侧 ENN 反馈"这一条件不可能成立 ——
   未来 arm 之前必须现场明确授权 SW1 动作；不得靠注释假装阻断位下也能正式使能。
 · 编译期宏只是其中一位：候选目标把 tmc2209.h:205 的 HW_NOT_VALIDATED 与 motor.h:89 的
   ENABLE_PATH 两项从"永远置位"变成"取决于运行态"，其余各位（QUIET/READY/FAULT/LINK/FB）
   照旧拦 —— 这就是 §3.4 例外的真实边界，不构成任何硬件验收。
