# R7F8F：A 对两条静态预算红项的最终裁定

2026-11-05。承接远端 `6f2b12f` 的交接 §3、run_record §24.4。仍属同一 R7F8F，不另开离线任务，不增加现场动作。本补充给出确定的执行语义与38步时间表，由 B 并入当前派生件、计划、rows、判据与交接。**现场尚未批准、尚未执行。**

## 1. 裁定一：可信零速确认后结束运动计时，arm计时继续独立生效

采用交接列出的第二条出路。不扩大12秒运动上限、不增加第二次会话、不删commit或ps/free。运动计时从 `motor_start` 写入尝试起，到本次正常 `motor_stop` 之后的一份**新鲜、完整、可信的零速快照**为止。stop命令回话本身不能结束运动计时。

允许结束运动计时的唯一正常业务点：当前计划 `as=stopped`、命令必须为 `motor_status`、当前步骤的零速判据已通过，同时满足：

- 本会话已经尝试过唯一一次start，并有随后正常motor_stop的发送及成功响应；不能在arm之后尚未start时关闭一笔不存在的运动。
- 原始字节、完整回包、命令身份、危险文本门均通过；证据来自本次查询的同一份响应，不能借前面的零速记录或跨回包拼字段。
- `state=0`、`cur_hz=0`、`tgt_hz=0`、`health=OK`，且armed、请求、pad、ENN预期／反馈／verdict自洽。典型的stop后状态仍是armed1、HIGH/pad1、ENN LOW/0/resolved/OK；已经armed0时须是LOW/pad0、ENN HIGH/1/resolved/OK。CUT_BY_HARDWARE或不完整快照不作正常完成证据。
- 快照在本次start起12秒以内取得；12秒已到不能用一份迟到零速回包倒填为按时完成。

保留本次start的t0、最终确认时刻、原始文件散列和计算出的运动耗时。不要通过清空t0来允许第二次start。正常stop后零速未证时，运动12秒义务继续有效；首错仍进固定收口。

**零速确认不解除arm通电义务。** arm起18秒继续约束disarm及其相邻禁能快照。只有真实disarm成功行＋可信禁能快照才能关闭该义务。之后commit/show/ps/free继续受会话业务截止83秒约束。若这些前提没有取得，不能因为“按计划已经发过stop/disarm”放开时限。

运动确认结束后，MotionBudget不能继续把停机后的业务和清理夹在旧的`t_start+12`或`t_start+12+7`内；清理仍用独立7秒预留，并受会话90秒总截止封顶。尚未确认零速时，原有运动截止和撤能收口约束保留。会话末用于统计耗时的close不等于取得了零速证据；失败终态继续保留UNKNOWN。

这是主机依据软件快照管理预算的语义，不证明物理STEP最后边沿或实际转轴停止时延；没有新增仪器结论。

## 2. 裁定二：本轮计划使用显式单步总窗，不再逐步叠加旧3秒SLACK

本补充允许本轮计划申报 `step_total_seconds`：该值已经包含本步全部等待与余量，是**一次业务步骤的总窗**。非轮询步骤含发送尝试、完整回读及本步处理；轮询步骤含全部尝试、间隔与回读，不再给每次轮询另加窗口。所有过程继续取step、业务83秒、运动12秒、arm18秒中仍生效的最早截止。

由一个公共函数解析时限，供执行器、计划校验、预算镜像和仿真使用：

1. 本字段存在时，要求finite、正数、非bool；必须保留0.5等小数，不经int截断，也不再加SLACK。非法值在开口前具名拒绝。
2. poll.until_seconds不得大于本步总窗；本表四个轮询的总窗等于原定until_seconds，原次数和间隔都不变。
3. 字段缺省时继续按原有legacy规则执行，冻结R7F7及旧计划不改。不得把全局SLACK直接改成0，也不能让检查器用新窗口而执行器仍加旧3秒。
4. 任一步超窗立即首错收口，不延长、不重发、不重建作业。单步窗口是软件截止安排；不声称Windows／USB具有实时保证，独立SW1禁能仍保留。

38步的精确覆盖见 `step_total_windows.json`。命令、顺序、次数、N、方向、目标速度、学习窗及全部既有业务判据不改。以下为便于核对的分组：

| 总窗 | 步骤as |
| --- | --- |
| 13 s | zero |
| 2 s | apply、wait_done（后者为整个有界轮询） |
| 0.5 s | dir、target、start、learn_cancel、ls_cancel_bound、cancel、learn_done、stop、disarm |
| 1 s | 其余26步；cruise/cancel_state/stopped分别为原有整体轮询窗 |

缩短窗口只控制一次步骤的等待上限，不替换产品内部deadline。zero保留13秒总窗，未修改产品12秒deadline；其余0.5秒的短命令／作业回包由实际源码行形核串口传输下界，不能拿简化的stub行宣称已测Windows真实响应时延。迟到即停，不用重试挽救本轮。

## 3. 同一份表算出的预算

| 边界 | 累计／耗时上界 | 原上限 |
| --- | ---: | ---: |
| start前19步 | 31.0 s | 业务总窗83 s内 |
| 从start到正常stop发送尝试 | 7.5 s | 正常stop须在8 s内发起 |
| 从start到stopped零速确认 | 9.0 s | 运动12 s |
| 从arm到mot_disabled禁能确认 | 13.0 s | arm通电18 s |
| 零速确认后8步 | 7.5 s | 业务总窗内 |
| 38步总窗合计 | 47.5 s | 业务83 s |
| 总窗合计＋清理预留 | 54.5 s | 会话90 s |
| 以整段12秒运动cap保守替代9秒活动步骤后，再加停机后内容与收口 | 57.5 s | 会话90 s |

最后一行的算式是31＋12＋7.5＋7，不重复计算活动步骤。按同样方式，arm保守预算为2.5（arm到start）＋12（完整运动cap）＋1.5（零速到禁能）＝16秒≤18秒。

这些数是本表分配的窗口与计时合同，不是硬件实测耗时。运行时仍以单调时钟的真实耗时裁剪；线程调度、写盘或USB迟滞导致业务超界时，本场按失败收口，不能把上述表格当作成功保证。现场判读单独核stop实际TX是否≤8秒及真实零速／禁能时刻。

## 4. 两条红项如何真正转绿

- `PLAN_POST_SPIN_CONTENT_FITS_CAP`：改核start到**零速确认**的活动内容及运动cap；停机后的commit/show/ps/free不再属于运动cap，但仍属会话业务预算。零速结束点必须在实际执行路径中受证据门控制，不能只在静态表上切开。
- `PLAN_WORST_CASE_TAIL_FITS_SESSION`：按每步已含余量的总窗重算，并让实际read/poll/watch使用同一解析值。不能只把FAIL改N/A或增加expected失败名单。原来的91／23秒红原文继续保留，注明其对应旧“每步再加3秒／stop不解除运动计时”语义。
- 更新镜像字段为三段：pre_start 19步、motion_active 11步（含stop及stopped）、post_zero 8步；记录stop_request_index=28、zero_confirm_index=29（均0基）。不得把旧的post_stop起点继续当运动结束证据。
- post-stop rows应单列真实“零速但仍armed”的完整反馈形状，不用初态禁能快照顶替正常stop行为。真实返回若已经禁能，亦按完整自洽合同判断，不预编观察。

## 5. 同轮收尾所需验证

在原四族与整包验证上补有限的相关用例，不开发新框架：

1. stop ACK之后仍未零速，或仅有残缺／旧快照，不能解除运动12秒；迟到零速不能倒填按时完成。
2. 合法的新零速确认后，已成功disarm的commit／ps/free可以跨过旧`t_start+12`继续完成，仍被83秒业务截止约束。
3. 已零速但仍armed时等待到18秒，必须停止业务并收口；证明释放运动计时没有释放通电计时。
4. 第二次arm/start仍在写前拒绝；NUL／坏字节／矛盾字段／错误JOB_ID等门保持，首错不继续commit。
5. 0.5秒窗口实际保留小数、不叠加3秒；poll总窗不随次数刷新。按表延迟响应的正常链及各边界超时链分别验证；不得用所有响应瞬时返回的夹具代替预算行为验证。
6. 原清理五条发送机会、开IRQ但未arm的尾部、会话预留7秒、总截止90秒保持原反例覆盖。不得扩大动作额度。
