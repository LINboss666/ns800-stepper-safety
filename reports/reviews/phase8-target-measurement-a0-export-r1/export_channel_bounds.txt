1. 目标机制（逐条实读，行号来自本仓库当前字节）
====================================================================
BSP/novosns/ns800/ns800rt7p65-nssinepad/rtconfig.h:107   #define RT_CONSOLEBUF_SIZE 128
BSP/novosns/ns800/ns800rt7p65-nssinepad/rtconfig.h:125   #define FINSH_THREAD_STACK_SIZE 4096
rtconfig.h 里没有 RT_USING_THREADSAFE_PRINTF（grep 无命中），也没有 RT_KLIBC_USING_LIBC_VSNPRINTF。

src/kservice.c:391  static char rt_log_buf[RT_CONSOLEBUF_SIZE];        (128 B 静态缓冲)
src/kservice.c:405  length = rt_vsnprintf(rt_log_buf, sizeof(rt_log_buf) - 1, fmt, args);
                    ⇒ size 参数是 127：最多写 126 个可见字符，第 127 字节(下标 126)放 NUL
src/kservice.c:406-409  if (length > RT_CONSOLEBUF_SIZE - 1) length = RT_CONSOLEBUF_SIZE - 1;
src/kservice.c:411  _kputs(rt_log_buf, length);                        ⇒ 上线 length 个**原始字节**
src/kservice.c:341-361 _kputs() 在 RT_USING_DEVICE 且有 console 设备时走 rt_device_write(dev,0,str,len)
src/kservice.c:327-332 RT_USING_THREADSAFE_PRINTF 未定义 ⇒ CONSOLE_TAKE/CONSOLE_RELEASE 展开为空
src/kservice.c:369-381 rt_kputs(str) = _kputs(str, rt_strlen(str))      ⇒ 不经 128 B 格式化缓冲，不送 NUL

实际链接的 rt_vsnprintf 实现（这是本次核对的一个新增事实）：
  Keil 工程 bsp/.../project.uvprojx 的文件列表里是 **rt_vsnprintf_tiny.c**（不是 rt_vsnprintf_std.c），
  而 src/klibc/kstdio.c:81 的 libc 版被 RT_KLIBC_USING_LIBC_VSNPRINTF 编译掉。
  src/klibc/rt_vsnprintf_tiny.c:325-340 与 447-470 的写法是"先判 str<end 再无条件 ++str"，
  函数末尾 return str - buf ⇒ **返回值是"应当写出的总字节数"(C99 语义，不含 NUL)**，
  与实际写入量无关。这一条决定了 spm_emitfv() 的溢出判据
  `n < 0 || (rt_size_t)n >= sizeof(line)` 在目标上真的会触发（而不是死代码）。

结论：任何 >127 字节的 rt_kprintf 整行都会 (a) 被静默剪成 126 个可见字符，
(b) 丢掉自己的 \n（于是与下一行粘连），(c) 把一个 NUL 送上控制台。

4. 板级原始接收字节里的上线事实（离线读取已保存文件，未连接任何设备）
====================================================================
对象：`<RAWDATA>/serial/*.txt`（57 个文件，54927 字节；板级轮原样保存的接收字节。
     `<RAWDATA>` 的展开规则与本包 board_raw_archive.md 的变换表一致）

  NUL 字节总数                    146
  CRLF 对数 / LF 数               776 / 781  ⇒ 5 个孤 LF 全部在 01_reset_pyocd.txt，
                                   那是本机工具自己的 stdout 文本("…-c exit\nSTDOUT\nRese")，
                                   不是目标上线；目标上线的每个 LF 前面都有 CR。
  每个 NUL 与"上一个分隔符(LF 或前一个 NUL)"的间距直方图
                                   {126: 144, 12: 2}   ⇒ 恒等于"126 可见 + NUL = 127 上线字节"
     2 个 12 的特例都是同一行 [SS] STEP: ...post_eff=100\nsrc=emergenc\0
     —— 该格式串自带一个换行，剪断点落在第二个分句中间；它是 Safety 模块的历史长行，
     不在本轮修复范围内（§4.1.5 本轮不修所有模块的历史长日志）。

由此判定（不是猜测，是字节证据）：
  (1) 目标走 rt_device_write(console_device, 0, str, 127) 分支 ⇒ 被剪断时 NUL 真的上线；
      若走 drv_common.c:175 的 rt_hw_console_output(str) 分支，它按 rt_strlen 发送，NUL 不会上线。
  (2) 控制台设备层把 \n 展开成 \r\n（故采集门必须同时接受 LF 与 CRLF）。
  (3) 被剪断的行**没有**换行符，下一条紧跟其后（cmd_114_b1_dump.txt 里可见
      "...owner_after,phase_af" 直接粘 "2,1,0,trip_fast,..."），
      这正是"无法可靠分离就拒绝该批"的实测依据。

典型批次（头行 490 B → 上线 127 B）：
  cmd_114_b1_dump.txt   size=361  nul=2  (头行 + 1 条数据行 各被剪一次)
  cmd_135_b2_dump.txt   size=2267 nul=17 (头行 + 16 条数据行)
  cmd_108_spm_cap.txt   size=334  nul=1  (cap 三行里最长那条被剪)
