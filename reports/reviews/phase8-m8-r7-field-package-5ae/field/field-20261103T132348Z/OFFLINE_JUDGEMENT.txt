## 4. 失败事实与产品侧读法（只读已抓到的字节，未再动设备）

`fault=8` 就是产品自己的 `FAULT_SELF_TEST`（`applications/safety_state.h:48`），生产者正是那条
required 项失败：`[SS] [REQ FAIL] TMC2209 IOIN read rc=-23`。本轮**不猜根因**：同一份流里
`[TMC] DEGRADED drive_cfg=UNCONFIGURED`、`[SNS] sensor thread started (100Hz)`、`>CUR … health=DEGRADED`
都在，rc=-23 与既有 RT-Thread 错误码表里的 -EBUSY 同数值——"读不到"与"总线还没让人读"两种机制
都还没被排除，需要下一轮用只读手段区分。归因待定，不据症状改产品代码。

安全侧字段（同一份流里 `=== SYSTEM STATUS ===` 的原文）都是"停在安全态"的证据：
`[Safety] gpio_ready=YES thread=OK drv_en_pad_low=YES`、

## 5. A 的校正在这一次现场起了作用（可核对的两点）

1. 白名单生效：`BUSINESS_OUTCOME allowed=false, status_lines_allowed=["[Motor] arm gate fail mask=0x1A (arm REFUSED)"]`
   —— 那条披露行被放行，停因而不是"动作被拒"误判；A 指出的"原 R7 会把正常启动回包误拒"这条
   在本场表现为**没有**误拒。
2. 连字符取值可用：`[Safety] … polarity=not-confirmed …` 被接受（原 `\w+` 会拒绝），
   停因落在真正的值不符上：`state=FAULT_LATCHED≠READY`、`fault=8≠0`。
   即校正版把"误拒"与"真失败"分开了——这条只能由这次真实字节说明，不能由离线判据说明。

## 6. 短打印：本包目标行未到达，行宽事实按抓到什么说什么

- `[SAFETY] LIMIT inputs config =` / `[SAFETY] LIMIT OFF => …` 所在的 `safety_irq_status` 步骤**没跑到**
  （S3 在第 2 步 sysboot 就停）；`[TMC-CFG] CONFIGURED …` 三条所在的 S4 整段未跑。
  这两组判据现场状态仍是 **NOT_VERIFIED**，不算通过也不算失败。
- 本次真实字节能说的行宽事实：
  * `system_status` 单条响应（`S_S3/02_sysboot.rx.bin` 992 B，无裸 NUL，UTF-8 完整）：21 行，
    **最长 120 B，超 120 B 的行 0 条**。
  * 启动被动流（多线程并发打印）：75 个分段里 **2 个分段超过 120 B（252 B / 305 B）**，
    其形态是同一条分段里咬着 2～3 次不同的打印（分段 29 含两次 `[MOT]`，分段 48 含三次 `[SS]`），
    并且整流有 **3 个裸 NUL**（偏移 1318 / 2268 / 2395）、整体 **UTF-8 解码异常**（首错偏移 1317）。
    也就是说：单次 printf 拆到 <=120 B 并不能保证**流里的行** <=120 B——并发期间会互相咬，
    这与既有的控制台 128 B 裁剪观察一致，但本轮不再补测、不择一归因。
- 登记执行器覆盖缺口（本轮不修）：命令响应路径有"危险文本 → 裸 NUL → 非法 UTF-8"三级硬门
  （`RX_DONE` 里 `nul_bytes=0` 即此门），而被动启动流只调 `check_danger()`（`m8r3_serial_chain.py:1804`
  附近），**不判 NUL/UTF-8**，所以本场的 3 个 NUL 没有成为具名失败。启动流里出现这种字节
  是否应当 STOP，属于判据设计问题，交给 A 定；本轮既不放宽也不擅自收紧。
