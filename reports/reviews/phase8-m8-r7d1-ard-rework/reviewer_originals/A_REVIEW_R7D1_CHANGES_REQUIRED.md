# R7D1 独立复审与离线返修任务

结论：**CHANGES_REQUIRED，暂不签收。** 受审提交 `4d503103cf3f1eb6f5113b10cc8683954d510ac6`。原有 62 个 host 用例与 14 组反向注入均独立复跑成立，但额外四个边界反例均失败。下面四项是产品 C 的错误路径缺陷，不能用现有全绿结果抵消。

## 一、四项需要修复的缺陷

位置均在 `rt-thread-master/rt-thread-master/bsp/novosns/ns800/ns800rt7p65-nssinepad/applications/diag_relative.c`，行号对应受审提交。各项按 P2 登记；这里没有把 host 反例升级为现场故障或物理保护失败。

### ARD1：NULL 状态查询在成功取锁后返回，遗漏放锁（1540–1542）

`rel_job_status(RT_NULL)` 先执行 `rel_ctx_take()`，随后直接返回 `-RT_EINVAL`。当取锁成功时，没有 `rel_ctx_give_held()`。

独立输出：`rc=-5 ctx_held=1 takes=1 releases=0`。这证明非法参数路径泄漏一层锁；实际跨线程访问可能因此长期拿不到上下文锁。当前正常 CLI 查询传入有效地址，不能把这个反例说成“每次查询都会锁死”。

修复要求：参数拒绝不得留下锁或其他副作用。加入非法参数后仍能正常查询、推进和取消的回归；不得通过测试重置锁来冒充正常恢复。

### ARD2：zero 的退出清理拿锁失败后，采集器归属永久滞留（1499–1504、1893–1897）

`rel_zero_capture_close()` 拿不到上下文锁就静默返回。它没有向调用者披露未清理状态，也没有后续回收路径。`rel_job_advance()` 仅推进 JOB 归属，无法替 ZERO 收口。

反例先让 pending 快照与采集器受理两次取锁成功，再使凭据作废与退出清理两次取锁失败：zero 命令退出时 `owner=BY_ZERO active=1`。解除注入并允许后台推进后，再次 zero 仍报 `capture busy`，归属没有恢复。

修复要求：所有 zero 退出分支都要保证清理最终可达。可采用有界延迟清理，但必须有明确状态与真实推进者，并在故障消失后释放本次资源；清理完成前不能交给第二个采集者。不得用无界等待、强行解锁他人锁、直接抹掉 owner 而保留活动采集器等办法凑绿。覆盖失效、超时、事务拒绝及发布失败等共享此清理函数的出口。

### ARD3：clear 在静止事务拒绝之前，已擦除候选和凭据（2165–2167）

先正常 zero、巡航 learn 到 DONE，再保持巡航执行 `clear CONFIRM`。静止事务如预期拒绝，但 `rel_pending_write(&blank, 0, 0)` 已经执行。命令输出 REFUSED，候选却被改写，zero/learn 凭据均被清零。

这是有旧版本对照的回归：

| 实现 | clear 静止门拒绝 | pending 改变 | zero / learn 凭据 |
|---|---|---|---|
| 旧基线产品 C | 是 | 否 | 1 / 1 |
| R7D1 `4d50310` | 是 | 是 | 0 / 0 |

旧基线控制运行使用 `0cd6458` 的完整 host 环境；其产品应用与 host 测试目录相对 `7885aea` 没有改动，差异核对见 `IDENTITY.json`。两组都经过实际 zero/learn 命令建立凭据，没有直接伪造成功候选。

修复要求：先完成全部必要门禁，再产生 clear 副作用；被拒绝的命令保留原候选、凭据及配置。配置清理本身失败时的事务语义也须明确，不能把“更保守”当成允许拒绝后暗改状态的理由。

### ARD4：commit 报 REFUSED 时，RAM profile 已经写入（2140–2148）

在有效 learned 候选与静止条件下，让 gate、两次候选快照取锁成功，`project_config_set_rprof()` 成功，然后使候选发布的取锁失败。

输出为 `commit REFUSED: (ctx-lock-publish) rc=-12`，但配置快照的 magic 从 `00000000` 变成 `4E535250`，配置内容已经改变。这里证明的是 **RAM 中的项目配置改变**，没有运行 `config_save`，不是 Flash 持久化证据。

修复要求：配置与候选发布有完整、一致的事务结果。若 REFUSED，配置、候选和凭据均保持原值；若 OK，配置和候选完整一致。不能仅改输出文字、吞掉失败或保留半份发布来通过验收。保留叶锁规则，不在该锁内引入 UART、sleep、Flash 或会再取其他锁的调用；如需要调整直接依赖的配置事务接口，记录锁序与边界即可，属于本轮离线修复范围。

## 二、复现方法与证据范围

`reproducer/review_probes.c` 直接包含仓库现有 `tests/host/rel_main.c`，后者编入实际产品 C；不复制替代产品算法。复用的 RTOS、时钟、传感器和运动环境仍为原 host 模型，不能视为真实 RTOS 调度或硬件时序证明。

在受审分支或其修复分支的仓库根上运行，输出放到仓库外：

```text
python reproducer/run_review_probes.py --repo-root D:/ns800 --out C:/r7d1_a_review_probes
```

要求已有 Python 3 和 GCC。脚本只编译、执行 host 程序，不访问串口、DAP 或分析仪。在本提交上预期 `REVIEW_SUMMARY|checks=4|failures=4|hardware_actions=0`，进程 rc=1；修复后应为四项业务断言全部通过、rc=0。rc=4 是环境/前置失败，不计业务检出。修复可以改变内部取锁顺序；若需调整故障注入锚点，保留上述业务触发意图及可触发性，不把锚点失效算成通过。

`proof/review_probes/` 保存本次发布版复现程序的原始编译与运行输出。`proof/original_replay.log` 是原有 62/62 与 14/14 META-OK 的独立重跑。`clear_control.c` 与两份输出提供 ARD3 旧/新对照。

Linux 原样运行现有 runner，首次因 host 头文件引用 `windows.h` 而未能编译（未执行业务用例）。本次随后只在仓外增加空 `windows.h` 兼容头：这条 M8 host 编译链未调用 Win32 API，不替代 RTOS 或产品行为。成功重跑使用 GCC 14.2；该工具链对旧 fixture `adxl345_read_mg()` 同行三个 if 报 1 条 misleading-indentation 警告，不能把本次 Linux 编译称为 0 警告，也不据此否定原交付的 Windows 工具链记录。

复现草稿曾缺少与原 main 相同的启动释放及静止前置，准备断言未通过；已补齐后重新运行，只有最终日志被用于以上四项结论。脚本和产品仓库彼此分离，A 未修改产品源码、未提交或推送变更。

另已独立核算归档 BIN 为 297004 B，SHA256 `df7584c3df2e682d07564ee70f05ecc7b608052a7fa739fb0c21b4f942b15c2b`；归档 AXF 的 Flash 装载段与 BIN 逐字节相等。A 没有重跑 Keil/ARM 产品构建，也没有将资源/镜像一致性当成四项代码正确性的替代证明。
