2. M0-E1：`state=4` 不是 IDLE，也不许写"Motor 正常静止"
==============================================================================
  已发布原句（cp1_target_fault_analysis.txt §6）：
    · 六条 MCU 侧状态全部可读且互相自洽（Safety 锁存=自检拒绝、许可 LOW+回读=0、ENN 在禁能侧、Motor IDLE/armed=0、STEP 通道未占用）=> 通信面 MCU 一侧正常，链路问题在 UART2↔TMC 之间。
  两处收紧都不成立，按下面更正：
    motor.h:111  MOTOR_IDLE = 0,     /* 未 armed 或已减速到 0 */
    motor.h:112  MOTOR_ACCEL,
    motor.h:113  MOTOR_CRUISE,
    motor.h:114  MOTOR_DECEL,
    motor.h:115  MOTOR_FAULT,        /* 紧急停机后锁定 */
  实读枚举 = MOTOR_IDLE 0 / ACCEL 1 / CRUISE 2 / DECEL 3 / **FAULT 4** ⇒ 本轮 `state=4` 是 **MOTOR_FAULT**。
  更正口径：`[MOT] state=4 armed=0 cur=0 tgt=0` 只说明"Motor 处于故障锁定、未 armed、软件命令速度与目标为 0"；
    `cur/tgt=0` 是**软件命令值**，不是"物理无脉冲"的测量；`[STEP] enabled=no last_stop=not-attempted`
    描述的是**诊断路径**未占用该通道，不能单独推出"STEP 引脚从未输出过"。
  原句的后半"通信面 MCU 一侧正常，链路问题在 UART2↔TMC 之间"同样**过强**：COM5 是主机控制台，
    控制台可查询只证明 msh/uart2 设备打开这一段，不证明 UART2 时钟、引脚、波特率、模块接口正常；
    且超时可能发生在**还没发出请求**之前（见 §3），所以不能把范围写成"UART2↔TMC 之间"。

3. M0-E2：`-117` 只到"IOIN 读操作报告超时"，且出口比我原来说的多
==============================================================================
  已发布原句（§2）："仍未收敛到的（必须保留为未知，不得写"已定位"）：同一 -RT_ETIMEOUT 有三个阶段能产出，"
  —— **出口数目偏少，且漏掉两个关键出口**。
  本轮把 `APP/tmc2209.c` 里每一条 `return -RT_ETIMEOUT` 连同**所在函数**与**已置 reason**定位并断言（共 13 处）：
    :309   tmc_rx_flush()         reason=TMC_XFER_BUDGET_EXHAUSTED
    :336   tmc_rx_flush()         reason=TMC_XFER_RX_FLOOD
    :347   tmc_rx_flush()         reason=TMC_XFER_BUDGET_EXHAUSTED
    :389   tmc_tx_frame()         reason=TMC_XFER_BUDGET_EXHAUSTED
    :419   tmc_tx_frame()         reason=TMC_XFER_BUDGET_EXHAUSTED
    :424   tmc_tx_frame()         reason=TMC_XFER_TX_FAILED
    :563   tmc_read_reg_locked()  reason=TMC_XFER_BUDGET_EXHAUSTED
    :569   tmc_read_reg_locked()  reason=TMC_XFER_RX_TIMEOUT_PART
    :591   tmc_read_reg_locked()  reason=TMC_XFER_RX_TIMEOUT_ECHO/PART(:586-:588 三元, n==0 与无匹配头合并)
    :609   tmc_read_reg_locked()  reason=TMC_XFER_BUDGET_EXHAUSTED
    :632   tmc_xfer_take()        reason=（该出口不写 st->reason）
    :1345  tmc_cfg_lock_take()    reason=（该出口不写 st->reason）
    :1415  tmc_cfg_hw_open()      reason=TMC_XFER_BUDGET_EXHAUSTED
  其中**一个字节都还没上线**就能返回 -RT_ETIMEOUT 的出口：:389 :632 :1345 :1415 —— :389 在 :397 真正写之前；
    :632/:1345 在取锁前看剩余预算；:1415 在发起 open 前看剩余预算。
  阶段归类（今后引用超时不许再写"三个阶段"）：
    ① 请求发出前（不碰线）：:1345 配置事务锁 / :1415 hw open / :632 传输锁 / :389 TX 预算；
    ② 排空 RX 阶段：:309/:347 预算、:336 RX 洪水（"没排干净"本身也报超时）；
    ③ 发送阶段：:419 写后预算、:424 末字节写出之后才判逾期（字节**可能已上线**）；
    ④ 接收阶段：:609 轮询中空窗越过预算、:591 未拿到匹配完整帧（reason 把"0 字节"与"有字节无头"合并）；
    ⑤ **帧已完整且 CRC 已过**：:563 总预算为 0、:569 阶段期限已过 —— 这两条意味着
       "芯片可能确实回答了，只是被判迟到而不发布成功"，因此**禁止**写"已证明芯片无应答"。
  与复审 §4 表逐条对齐的源码事实：
    · :632 `tmc_xfer_take()` 在**剩余预算为 0** 时直接返回 -RT_ETIMEOUT —— 此时本次请求一个字节都还没发；
      它既不是 :628 的 `tmc_lock_ok`（-RT_ENOSYS=45），也不是 :634 的取锁失败（-RT_EBUSY=23）。
      ⇒ 我原句"排除了取不到事务锁这一类"只对了一半：被排除的是 ENOSYS/EBUSY 两个码，**不能**排除"进锁前预算已耗尽"。
    · :559 与 :565 —— **完整帧且 CRC 已通过**，仅因总预算/阶段期限过期而 `不发布成功`（:569 注释原文）。
      ⇒ "芯片完全没回答"这种写法禁止：本轮证据允许"芯片答了但迟到被拒"这一可能。
    · :580-:591 未拿到匹配完整帧的超时分支；:586-:588 把 `n == 0`（一个字节都没收到）与
      "有字节但没找到应答头/回声" **合并**成同一个 `TMC_XFER_RX_TIMEOUT_ECHO`（:91 定义，:187 字符串 "rx-timeout-echo"）。
      ⇒ 该枚举名**不能**当"确实收到了回声"的证明；要区分必须同时导出字节数与帧事实。
    · :548-:552 CRC 比较失败是另一个直接出口（-RT_EIO=12），与本轮 -117 不同；但不能据此排除噪声/丢字节/短帧。
  正确的结论措辞（今后一律照此）：**第 7 条 `tmc_uart_probe` 的 IOIN 读操作返回 -RT_ETIMEOUT（报告超时），
    TMC 链路仍 LINK_UNPROVEN**；阶段归属、芯片是否应答、TX 还是 RX 侧，全部保留为未知。

4. M0-E3：码表推导本轮闭合到仓内文件（我原句缺了 `!RT_USING_NANO` 这一半前提）
==============================================================================
  已发布原句：RT_USING_LIBC=1（走 POSIX 兼容分支）、RT_ETIMEOUT=ETIMEDOUT、ETIMEDOUT=(ERROR_BASE_NO + 110)、ERROR_BASE_NO=7
  —— 只写了 `RT_USING_LIBC=1`，**没写**"且 RT_USING_NANO 未定义"；该条件是分支的一半；
    kerrno.h:21   #if defined(RT_USING_LIBC) && !defined(RT_USING_NANO)
    kerrno.h:25   #define RT_ETIMEOUT                     ETIMEDOUT       /**< Timed out */      <- POSIX 分支
    kerrno.h:45   #define RT_ETIMEOUT                     2               /**< Timed out */      <- 数字分支（本配置未走这条；若走了应是 -2 而不是 -117）
  ERROR_BASE_NO 也有三个分支，取哪一个由编译器宏决定：
    errno.h:14/:26   #if defined(__ARMCC_VERSION) / #define ERROR_BASE_NO    7
    errno.h:28/:35   __IAR_SYSTEMS_ICC__ → #define ERROR_BASE_NO    36（IAR，未采用）
    errno.h:38       #define ERROR_BASE_NO    0（其他，未采用）
  默认目标（= 板上那份镜像的构建配置）armclang 预定义转储实测：
    __ARMCC_VERSION=6240002   RT_USING_LIBC=1   RT_USING_NANO=（未定义）   ERROR_BASE_NO=7
    ETIMEDOUT=(ERROR_BASE_NO + 110) = 117 ｜ EBUSY=23 ｜ EIO=12 ｜ ENOSYS=45 ｜ EINVAL=5（armcc 保留值，不机械套 7+22）
  ⇒ `-117` = `-RT_ETIMEOUT` 的推导**不依赖**任何桌面 errno 教材值；观测值与算式在 117 处相等（断言通过）。

  ⚠ 我当场口头给过一条**不该给的推论**（登记为 M0-E3b 并撤回）：曾说"RX 拿到 0 字节，连自身回声都没有，  所以指向线/供电被钳住"。该推论不成立：COM5 的被动窗口字节数与 **UART2 侧**的 rx_bytes 是两回事，  后者没有任何只读命令导出；而且 :586-:588 把"0 字节"与"有字节但无匹配头"合成同一个 reason 名。  撤回后保留为未知，不据此排障。
  另：用户提议"把 TMC 的 ENN 拉到使能再试"，我方**未执行**。依据是本仓 10-22 的真机实录——
