== 1. 改了什么(唯一一处产品改动) ==
  applications/diagnosis.c:48   +#define DIAG_THREAD_STACK   4096   /* 三帧静态下界 1064 B, 旧值 1024 装不下 */

  命名与同目录既有约定一致(motor.c:90 MOTOR_THREAD_STACK=2048, sensor_service.c:35 SENSOR_THREAD_STACK=4096)。

== 2. 为什么这一处是"确定的缺陷"而不是猜测(实读源码 + 实读构建产物) ==
  2.1 调用边(实读 rt-thread-motor-m1.map 交叉引用表):
        diagnosis.o(.text.diag_thread_entry) refers to diag_relative.o(.text.rel_prod_evaluate)
        diag_relative.o(.text.rel_prod_evaluate) refers to diag_relative.o(.text.rel_engine_step)
      => 三个帧在同一条直接调用链上, 会同时存在于栈内。
  2.2 每帧固定占用(实读**已接受的 R3 AXF** 全文反汇编, 与 armlink 调用图互证):
        diag_thread_entry  PUSH {r7,lr}(8) + SUB sp,#0x270(624) = 632 B   armlink: Stack size 632 bytes
        rel_prod_evaluate  PUSH {r7,lr}(8) + SUB sp,#0xf0 (240) = 248 B   armlink: Stack size 248 bytes
        rel_engine_step    PUSH {r7,lr}(8) + SUB sp,#0xb0 (176) = 184 B   armlink: Stack size 184 bytes
        三帧之和 = 1064 B > 旧配置 1024 B(复审给的**下界**口径, 本机逐地址复算一致)
  2.3 armlink 自己的累计值(新构建调用图, 比下界更强):
        diag_thread_entry  [Stack]Max Depth = 1580 B
          链: diag_thread_entry => rel_prod_evaluate => rel_prod_publish => rel_ctl_take => rt_mutex_take => _rt_mutex_take => rt_thread_suspend_to_list => rt_sched_thread_timer_stop => rt_timer_stop => rt_spin_unlock_irqrestore => rt_exit_critical_safe => rt_exit_critical => rt_schedule => rt_scheduler_stack_check => rt_kprintf => rt_vsnprintf => print_number => divide
        rel_prod_evaluate  [Stack]Max Depth = 948 B
        rel_engine_step    [Stack]Max Depth = 352 B
      镜像级: Maximum Stack Usage =       2996 bytes + Unknown(Cycles, Untraceable Function Pointers)
      => 1580 > 1024: 旧配置连 armlink 静态已知的该线程最深链都装不下, 不是"可能不够"而是"必然不够"。
  2.4 这条路径在 MONITOR_ONLY 下也执行(实读 diagnosis.c:446):
        (void)rel_prod_evaluate(&a, (rt_uint8_t)d_mode, &post_rc, &acted);
      模式是**实参**, 调用本身无条件发生在 diag 循环里; :445 的注释说明只有"真实 post"才分模式。
      => 不能用"当前是 MONITOR_ONLY 所以不走"来解释掉。

== 7. 本轮**没有**证明的东西(不得读成已闭环) ==
  1) 4096 不是已验证上界 —— 复审也是这么定的。armlink 镜像级写着 "2996 bytes + Unknown
     (Cycles, Untraceable Function Pointers)", 静态调用图本身不给闭合上界; 异常进入线程栈的硬件压栈
     (M7 视 FP 上下文 104 B 起)不计入。
  2) "diag 栈溢出就是本次链表坏指针的来源" **未证**。已证的只有: diag 的静态已知最深链 1580 B 超过它
     原来 1024 B 的栈 —— 这是一条确定缺陷, 与板子上那次 HardFault 之间的因果还需板上对照。
  3) 复审给的第二条线索(r1=0x20015b78 与 r3=0x20015b28 相差 0x50 = 线程内置定时器偏移;
     保存的 1024/18/10 与 bblog 的创建参数相符 => 坏的是**定时器对象链表**)本轮只登记为**有依据的推断**:
     offsetof(rt_thread, thread_timer)==0x50 尚未从 DWARF/布局独立核得, 且 r4..r6 与 §14.2 同类,
     本身是残留寄存器。见 §8 的板上判定动作。
  4) 新镜像在板: NOT_EXECUTED(本轮零设备动作, 板上仍是 R3 的 00608ec9…e304 与 Halted 的核心)。

== 8. 交给下一次批准的板级对照动作(本轮只列, 不执行) ==

  -> 串口查询 -> 栈观察; 零电机动作。
  两条**便宜的判定项**(在旧镜像仍 Halted、尚未下载之前做, 各一次只读 RAM):
    A. 读 0x200127D8 起 40 B = rt_object_init 出错前的局部槽 -> 直接给出 type/information/name,
       即"哪一个对象类的表"; 复审已按浮点扩展帧把出错前 SP 修正为 0x200127D8(见 run_record §15.1),
       这些槽**没有被异常帧覆盖**, 我上一轮判错了。
    B. 读 0x20015b28 起 48 B = 推断的 TCB 起点 -> name 字段(offset 4)会直接印出线程名,
       一次判定"是不是 bblog""r1 是不是它的 thread_timer"; 顺带核 offsetof(thread_timer)==0x50。
