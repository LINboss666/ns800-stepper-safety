## 错误码速查表（本工程实际取值，先看这个再猜错误码！）

本工程 `RT_USING_LIBC + ARM Compiler 6`，错误码走 RT-Thread `components/libc/compilers/common/extension/sys/errno.h` 的 **ERROR_BASE_NO=7** 分支（不是教科书上的 POSIX 值！）：

| 符号 | 实际值 | 符号 | 实际值 |
|---|---|---|---|
| RT_EOK | 0 | RT_EINVAL | **5** |
| RT_ENOMEM | **6** | RT_EPERM | 8 |
| RT_ENOENT | 9 | **RT_EIO** | **12** |
| RT_EAGAIN | 18 | **RT_ENODEV** | 26 |
| **RT_EBUSY** | **23** | RT_EEXIST | 24 |
| RT_ETIMEOUT | 117（ERROR_BASE_NO+110） | RT_ENOSPC | 35 |

**实战对照**：
- 串口看到 `FAIL (-23)` ≈ **EBUSY**（总线被占 / 器件写保护）
- 串口看到 `FAIL (-12)` ≈ **EIO**（传输失败 / 数据比对不匹配）
- 不要拿 POSIX 教材的 errno 值（EBUSY=16、ENOMEM=12）来套！这是 BUG-004 排查时浪费时间的直接原因。

## BUG-001：SPI 总线竞争 —— 两颗 Flash 的 CS 浮空导致读数错乱

- **日期**：2026-09-10 深夜
- **现象**：同一根 CS 线（PA19）读 W25Q64，有时读到正确 `EF 40 17`，有时读出稳定的 `16 16 16`；且换固件后结果不一致。
- **排查过程**：
  1. 先怀疑软件回归，diff 前后固件——差异不在执行路径上，排除。
  2. 硬件复位（pyocd reset -m hw）无效，排除外设卡死。
  3. 读原理图 PDF 第 2 页：板载 U4 (W25Q64JVSSIQ) 的 CS#=SPI1_NSS(PA19/J2-13)，DI/DO/CLK 接 SPI1_SIMO/SOMI/CLK——**与用户杜邦线外接的 Flash 模块（CS=PF12/J2-12）共享同一组总线**。
- **根因**：用户外接模块的 CS 在 PF12，而 MCU 固件访问 PA19 上的器件时，**PF12 是浮空输入**。浮空电平意外跌到低电平 → 外接模块被误选中 → 两颗器件同时驱动 MISO → 总线冲突，读出垃圾。之前"有时能读对"是因为浮空电平恰好没跌下去。
- **修复**：`main.c` 增加 `flash_cs_idle_high()`，上电即把 **PA19、PF12（以及后来加入的 PA20 IMU CS）配置为输出高**——任何时刻只有被访问器件的 CS 被驱动拉低。
- **修复后验证**：PA19 访问读到全 FF（U4 确实未焊，符合原理图"实际不焊接"标注）；PF12 访问稳定读到 EF 40 17。
- **防复发检查项**：
  - [ ] 共享总线上的每个 CS 引脚，上电第一件事就是输出常高（INIT_APP_EXPORT 或 main 最前面）
  - [ ] 新增 SPI 器件时，检查它所有未选中时的 CS 是否有确定电平
  - [ ] 杜邦线阶段的"灵异现象"先查浮空引脚，再怀疑软件

## BUG-002：新版 RT-Thread SPI 框架的 rt_spi_configure 返回 EBUSY 不是错误

- **日期**：2026-09-10 深夜
- **现象**：`flash_id`（flash_demo.c）报 `configure failed: -23`；`ns_flash_init` 同样位置失败。旧仓库（旧版 RT-Thread）同样的代码工作正常。
- **排查过程**：追 `rt_spi_configure` → `rt_spi_bus_configure`（components/drivers/spi/dev_spi_core.c）：
  ```c
  if (device->bus->owner == device) {
      result = device->bus->ops->configure(...);   /* 重新配置硬件 */
  } else {
      result = -RT_EBUSY;   /* ← 总线被别的设备占用 */
  }
  ```
  源码注释原话："RT_EBUSY is not an error condition and the configuration will take effect once the device has the bus"。
- **根因**：**新版 SPI 框架改变了语义**——当总线 owner 是其他设备时，`rt_spi_configure` 只保存配置并返回 `-RT_EBUSY`，等本设备下次拿到总线时自动生效。旧版内核这里返回 RT_EOK。旧代码把 EBUSY 当致命错误处理，直接放弃。
- **修复**：所有 `rt_spi_configure` 的检查改为 `if (e != RT_EOK && e != -RT_EBUSY)`。涉及 `flash_demo.c`、`ns_flash.c`。
- **防复发检查项**：
  - [ ] 新写 SPI 设备驱动：configure 后 `RT_EOK || -RT_EBUSY` 都放行
  - [ ] 从旧版 RT-Thread 移植 SPI 代码时，必查此处
  - [ ] 同一总线上多设备轮流访问是常态，EBUSY 是正常路径不是异常

## BUG-003：W25Q64 模块出厂自带块保护（SR1=0xFC），一切擦写报 EBUSY

- **日期**：2026-09-11 凌晨
- **现象**：`flash_info` 能正确识别（JEDEC=EF 40 17，SR1=FC），但 `flash_test run` 擦除即失败 `-23`。
- **排查过程**：读 `ns_flash_erase` → `writable()`：
  ```c
  if ((s1 & 0x1c) || (s2 & 0xc0) || (s3 & 0x04)) return -RT_EBUSY;
  ```
  SR1=0xFC = 1111_1100，`0xFC & 0x1C = 0x1C ≠ 0` —— **BP0/BP1/BP2 块保护位全部置位**。回查旧会话记录 `CMD=04 SR1=FC`，该模块从到手起就带着保护位，从未被清过。
- **根因**：模块状态寄存器的块保护位（BP0-2）被置位（出厂态或历史遗留），W25Q 擦写前必须清除。驱动的 `writable()` 只是如实上报保护状态（设计哲学：**不静默解锁**）。
- **修复**：新增 `flash_unlock` 命令（ns_flash_shell.c）+ `ns_flash_clearwp()`（ns_flash.c）：WREN → WRSR1=0x00（清 BP/TB/SEC/SRP1）→ 按需 WRSR3=0x00 → WRDI → 回读校验。保护清除是**用户显式命令**，不在 init 里偷偷做。
- **修复后验证**：SR1: 0xFC → 0x00，flash_test run / flash_verify 全 PASS。
- **防复发检查项**：
  - [ ] 新到手的 SPI Flash 模块，先 `flash_info` 看 SR1，BP 位非零先 `flash_unlock`
  - [ ] "能读不能写"先查状态寄存器保护位，再查时序
  - [ ] 驱动保持"不静默解锁"设计，解锁必须显式命令

## BUG-004：SR3 读出恒 0xFF —— W25Q64FV 与 JV 同 JEDEC 但没有 SR3 寄存器

- **日期**：2026-09-11 凌晨
- **现象**：`flash_unlock` 清 SR1 成功（0xFC→0x00），但 SR3 恒为 0xFF，`writable()` 的 `s3 & 0x04` 判断永远失败，仍报 EBUSY。
- **排查过程**：
  1. 第一次怀疑时序：WRSR 前需要 WREN，且 WEL 在每次 WRSR 后自清零——修正为每次写寄存器单独 WREN + 等 WIP 清零。SR1 清干净了，SR3 依旧 0xFF。
  2. 结论：0x15（读 SR3）/0x11（写 SR3）在这颗芯片上不受支持，MISO 浮空被上拉读成 0xFF。
  3. 查资料：W25Q64**FV** 与 W25Q64**JV** 的 JEDEC ID **完全相同（EF 40 17）**，但 FV 系列没有 SR3 寄存器。
- **根因**：**JEDEC ID 不能区分 W25Q64 FV/JV 子型号**，本模块是 FV 型（或等效无 SR3 的兼容片），驱动的 SR3 保护检查对它不适用。
- **修复**：驱动对 SR3 做"存在性探测"——读到 0xFF 视为寄存器不存在，跳过 SR3 相关检查与写入（涉及 `writable()`、`ns_flash_clearwp()`）。
- **防复发检查项**：
  - [ ] 涉及 SR3/WPS 的逻辑，必须容忍 SR3 不存在的芯片
  - [ ] Winbond 同 JEDEC 不同子型号（FV/JV/DTR）行为有差异，不要只信 JEDEC
  - [ ] "寄存器读出恒 0xFF"= 可能不存在该寄存器，不一定是真数据

## BUG-005：堆只有 16KB（实际 32KB），flash 测试缓冲分配失败

- **日期**：2026-09-11 凌晨
- **现象**：`flash_verify` 报 `-12`（ENOMEM）。
- **排查过程**：`board.h` 的 `HEAP_END = RW_RT_HEAD 限制 + 0x4000`，链接脚本 `RW_RT_HEAD 0x20012000 EMPTY 0x4000` —— 堆一共只有 16~32KB，里面还住着 tshell/main/idle 线程栈和 finsh，flash_test 还要 malloc 4KB+600B。
- **根因**：BSP 默认堆尺寸太小，多模块共存后碎片化+余量不足。
- **修复**：链接脚本 `RW_RT_HEAD EMPTY 0x8000`（32KB）+ `board.h` 偏移同步改 0x8000（实际可用 64KB，仍在 DTCM 范围内）。
- **防复发检查项**：
  - [ ] 新增大缓冲前看一眼 board.h 的 HEAP 配置
  - [ ] malloc 失败（-ENOMEM=6）先查堆水位，再查逻辑
  - [ ] 改堆大小时链接脚本和 board.h 两处必须同步

## 2026-09-11 新增经验（骨架开发日）

11. **RT_SERIAL_CONFIG_DEFAULT 是花括号初始化列表**：只能用于声明时初始化
    `struct serial_configure cfg = RT_SERIAL_CONFIG_DEFAULT;`，不能 `cfg = RT_SERIAL_CONFIG_DEFAULT;`
    （armclang 报 "expected expression"）。
12. **MSH_CMD_EXPORT 的描述参数里不能有逗号**：`(cmd, desc)` 逗号会拆参导致
    "undeclared identifier xxx_msh_options"。要写逗号就加括号。
13. **MSH_CMD_EXPORT 的命令名=函数名**：想让命令叫 `safety_state` 就得有同名函数
    （改名或用 MSH_CMD_EXPORT_ALIAS）。
14. **本工程 rtconfig.h 用 V1 串口框架**（RT_USING_SERIAL_V1），dev_serial_v2.h
    里的配置宏不生效。
15. **中文注释/字符串进串口会显示 ?**：串口助手按 GBK 显示而固件是 UTF-8，
    调试输出建议英文，文档里写中文。

## ⚠️ BUG-010：tmc2209.c 协议层三处错误（外部审查发现，协议层待重写）

- **日期**：2026-09-11（用户用 GPT 审查 GitHub 仓库发现，经官方源码+真机验证库双重核实，**指控全部成立**）
- **影响**：`tmc2209.c` 的 UART 通信目前**不可能与真实 TMC2209 通信成功**，整个协议层需要重写而非打补丁。`tmc_crc_test PASS` 是假阴性（见元教训）。

### 错误一：读/写方向位（bit7）写反了
- 我写的：读=`reg | 0x80`，写=`reg`
- 官方（TMC-API readRegisterUART/writeRegisterUART + 数据手册）：**读=bit7=0（`reg & 0x7F`），写=bit7=1（`reg | 0x80`）**，例：写 0x10 → 0x90
- 后果：发出的请求帧芯片按相反操作解读，永无正确应答

### 错误二：CRC8 喂位顺序错了
- 我写的：MSB-first（`crc & 0x80` 判断 + 整字节异或进 CRC）
- 官方（数据手册 C 示例 + TMCStepper 库 calcCRC，真机验证数十万设备）：**每个字节 LSB-first 喂入**：
  ```c
  if ((crc >> 7) ^ (currentByte & 0x01)) crc = (crc << 1) ^ 0x07;
  else crc = (crc << 1);
  currentByte >>= 1;
  ```
- 正确值实证（TMCStepper 算法）：读 IFCNT 请求帧 = `05 00 02 8F`；我的错误算法下同帧 = 0xAA

### 错误三：读应答第二字节校验错
- 官方读应答格式：`[sync 0x05][master地址 0xFF][reg][data31..0][crc]` —— 第二字节固定 **0xFF**
- 我写的校验 `r[1] != addr(0x00)` → 会把完全正确的应答判为错误

### 连带错误：写操作流程
- 官方（TMC-API）：写=fire-and-forget，**没有应答等待**；确认方式是 IFCNT 递增
- 我写的：写后等 4 字节应答并校验——错
- 正确的探活流程：读 IFCNT→N → 写一个安全寄存器 → 再读 IFCNT→N+1

### ⭐ 元教训（比 Bug 本身更重要）
`tmc_crc_test PASS` 是**自证陷阱**：离线向量用 python 算，但 python 脚本抄的算法和固件是同一套（都是我从同一个错误记忆里实现的）。代码注释里写了"防实现自证"，但**离线脚本与固件同源就根本不构成独立验证**。
→ 规则：协议类测试向量必须来自**第三方实现或官方文档的已发布示例**，不允许"自己算给自己对"。
→ 本次真正的独立验证链：GPT 指控 → TMC-API 官方源码（读写位/0xFF 应答/reflected CRC）→ TMCStepper 库真机验证算法复刻（0x8F 对上）→ 三方一致才算坐实。
- **处理**：`applications/tmc2209.c` 待整体重写；重写前 `tmc_uart_probe/tmc_status` 结果一律视为无效。

## ⚠️ BUG-011：安全骨架三处缺陷（外部审查发现，**接电机前必修门槛**）

- **日期**：2026-09-11（用户 GPT 审查指出，设计评审成立，非运行时故障）
- **共性**：都发生在"故障路径"上——正常路径测试测不出来，只在异常组合下暴露。

### 缺陷一：safety_enter_fault() 不执行停机，依赖调用方自觉
- 现状：函数只记 fault code + 置状态，注释写"停 STEP + 驱动禁止由调用方执行"
- 漏洞模型：A 路径（关 PWM→使能低→enter_fault）✅；B 路径（直接 enter_fault，忘了关输出）❌ —— 典型软件安全事故
- **修复方向**：唯一统一入口 `safety_force_shutdown(code)`：
  1. 停 STEP（pwm disable，容忍 pwm 设备未初始化）
  2. MCU_DRV_ENABLE(GPIO31) = LOW
  3. 记录 fault code → 状态 = FAULT_LATCHED
  所有严重故障只允许走这一个入口；原 safety_enter_fault 删除或成为其内部步骤

### 缺陷二：fault_reset() 没有实测故障源
- 现状：只判断 `state == FAULT_LATCHED` 就清故障，注释却写"仅在故障源已消失时允许"
- **修复方向**：清除前实测 ESTOP(GPIO70)/LIMIT(GPIO24,25)/DIAG(GPIO3) 电平，全部处于安全态才允许进入 MANUAL_CLEAR；任一仍处故障态则拒绝并打印

### 缺陷三：step_pwm 联锁的 fail-safe 方向反了（真实代码缺陷）
- 现状：`if (en >= 0 && rt_pin_read(en) != PIN_LOW) REFUSED;` —— `safety_pin()` 返回负值（引脚解析失败）时会**跳过检查继续开 PWM**
- 原则：**"不知道自己是否安全 = 按不安全处理"**（fail-safe）
- 修复方向：
  ```c
  if (en < 0) { REFUSED("enable pin unknown"); return; }
  if (rt_pin_read(en) != PIN_LOW) { REFUSED; return; }
  ```
- 该原则推广全项目：任何安全判定的前置信息不可得时，一律按不安全处理
- 注：当前因 BUG-009（GPIO31 写0读回1），联锁本就一直拒绝，未造成实际风险；但代码缺陷必须修
